метками (`set_name`, `operation`, `quantity`), поэтому результат удобно смотреть в DBeaver

## Мощности множеств (измеренные значения)

| Множество | Запрос в скрипте | Мощность | Пояснение |
|---|---|---|---|
| A (MA) | блок 2 | **657** | различных товаров куплено клиентами MA (717 delivered-заказов, 800 позиций) |
| B (PI) | блок 3 | **446** | различных товаров куплено клиентами PI (476 delivered-заказов, 523 позиции) |
| A ∪ B | `UNION` | **1046** | 657 + 446 − \|A ∩ B\| = 1046 |
| A ∩ B | `INTERSECT` | **57** | товары, купленные в обоих штатах |
| A − B | `EXCEPT` | **600** | 657 − 57 |
| B − A | `EXCEPT` | **389** | 446 − 57 |

Проверки непротиворечивости, которые выполняет скрипт:
`|A ∪ B| = |A| + |B| − |A ∩ B|` → 1046 = 657 + 446 − 57;
`|A| = |A − B| + |A ∩ B|` → 657 = 600 + 57;
`|B| = |B − A| + |A ∩ B|` → 446 = 389 + 57.

Обратите внимание: PI и MA — маленькие штаты (для сравнения, в SP 40 501 delivered-заказ),
поэтому мощности множеств небольшие. Это свойство данных Olist, а не ошибка запроса:
позиций в MA-заказах всего 800 (`count(*)` по проекции до `DISTINCT`), из них 657
различных товаров.

## Как устроены блоки

1. **Исходное отношение.** Показываем, какие таблицы используются и по какому ключу
   они соединяются: `orders.customer_id → customers.customer_id`, отношение 1:N.
2. **Пункт 1 — A и B.** `SELECT DISTINCT product_id` уже даёт множество, поэтому
   `count(*)` и `count(DISTINCT product_id)` совпадают (дубликатов не остаётся).
3. **Пункт 2 — `UNION` vs `UNION ALL`.** `UNION` удаляет дубликаты и возвращает 1046
   строк; `UNION ALL` склеивает списки без очистки: 657 + 446 = 1103 строки. Разница
   1103 − 1046 = 57 равна мощности пересечения — каждый товар из `A ∩ B` входит
   в объединение дважды.
4. **Пункт 3 — `INTERSECT`.** Даёт 57 товаров. В SQL `INTERSECT` по умолчанию
   работает как множество (`INTERSECT DISTINCT`).
5. **Пункт 4 — `EXCEPT` в обе стороны.** A − B = 600 (MA покупали, в PI — нет),
   B − A = 389 (только в PI).
6. **Пункт 5 — коммутативность.** Для `∪` и `∩` `(A op B)` и `(B op A)` дают пустую
   симметрическую разность в обе стороны, и обе разности равны 0, значит множества
   совпадают (порядок строк в SQL не сравниваем — сравниваем множества через `EXCEPT`).
7. **Пункт 6 — некоммутативность `−`.** |A − B| = 600 ≠ |B − A| = 389,
   а `(A − B) ∩ (B − A) = ∅` (0 строк): ни один элемент не входит в обе разности.
8. **Пункт 7 — пересечение через `EXISTS`.** Коррелированный подзапрос
   `EXISTS (SELECT 1 FROM B WHERE B.product_id = A.product_id)` даёт те же 57
   строк; обе разности `INTERSECT − EXISTS` и `EXISTS − INTERSECT` равны 0,
   то есть запросы эквивалентны.
9. **Пункт 8 — намеренные дубликаты.** Тот же `UNION` без `ALL` и с `ALL`: во втором
   варианте `count(*)` = 1103 > `count(DISTINCT product_id)` = 1046; сводка по
   `product_id` показывает 57 товаров, у каждого ровно 2 вхождения.
10. **Пункт 9 — множество vs мультимножество.** Сводная таблица: `SELECT` (без
    `DISTINCT`) и `UNION ALL` сохраняют кратность, а `UNION`, `INTERSECT`, `EXCEPT`
    её удаляют. Самый наглядный контраст — проекция `order_items.product_id`:
    112 650 строк против 32 951 различных товаров.

## Комментарий к пункту 9 (ответ на вопрос задания)

В SQL по умолчанию **множество** возвращают `UNION`, `INTERSECT`, `EXCEPT`
(эквиваленты с `DISTINCT`) и явный `SELECT DISTINCT`; **мультимножество** —
обычный `SELECT` (`π` без `DISTINCT`), `UNION ALL`, `INTERSECT ALL`, `EXCEPT ALL`.
Именно поэтому `count(*)` и `count(DISTINCT product_id)` отличаются: первый считает
элементы мультимножества с кратностями, второй — мощность множества.

## Контрольные вопросы

1. **Почему UNION обычно дороже UNION ALL?** `UNION` обязан устранить дубликаты:
   СУБД сортирует результат (или строит хеш-таблицу) и сравнивает строки, а это
   O(n log n) работы и лишняя память. `UNION ALL` просто конкатенирует наборы строк
   за O(n). В нашем примере `UNION` обработал 1103 исходные строки и вернул 1046,
   а `UNION ALL` вернул все 1103 сразу.
2. **Почему отсутствие ORDER BY делает неверным вывод о «порядке» кортежей
   отношения?** Отношение — это множество, у него нет порядка. SQL не обязуется
   возвращать строки в каком-либо порядке; планировщик может изменить его
   (индексный доступ, хеш-агрегация, параллельное выполнение). Поэтому сравнивать
   результаты двух запросов через первый `LIMIT`/`ORDER BY` без явного `ORDER BY`
   нельзя — сравниваем через `EXCEPT` в обе стороны (пункты 5 и 7).
3. **Чем множество отличается от мультимножества?** Во множестве каждый элемент
   присутствует не более одного раза, важен только факт принадлежности; в
   мультимножестве каждый элемент имеет кратность (число вхождений). Поэтому
   `count(*)` по мультимножеству может быть больше `count(DISTINCT ...)` по нему же.
