# Практика 11. Представления, CTE и рекурсивные запросы

Вариант 10: корень рекурсивного обхода — штат **GO**.
Файл `lab10.sql` выполняется сверху вниз в psql или DBeaver без ручного редактирования и
выполняется повторно (все объекты сначала удаляются через `IF EXISTS`, дерево пересоздаётся).
Все объекты создаются в схеме `lab`; исходные таблицы `olist.*` не изменяются.

Измерено на загруженном наборе Olist (PostgreSQL 17.5).

## Представление и материализованное представление

`lab.v_order_summary` хранит только определение запроса: каждый `SELECT` из него заново
выполняет соединение `olist.orders × olist.customers × olist.order_items`. Одна строка на заказ,
так как агрегирование идёт по `order_id`. Заказы без позиций остаются в отчёте через `LEFT JOIN`,
их 775 из 99 441 (все с `items_count = 0` и суммой 0). Контроль: **99 441 строка** представления =
99 441 строка `olist.orders`, суммарно **112 650 позиций** и **15 843 553,24** — ровно как в
`olist.order_items`. Среднее число позиций на заказ — 1,13.

`lab.mv_monthly_state_sales` физически хранит результат: **559 строк**, 24 месяца
(2016-09 … 2018-09) и 27 штатов; `sum(sales_value)` = **15 843 553,24**, совпадает с суммой по
`olist.order_items`. Данные устаревают, пока не выполнена команда

```sql
REFRESH MATERIALIZED VIEW lab.mv_monthly_state_sales;
```

Она стоит в скрипте отдельным оператором после создания. Уникальный индекс
`(month, customer_state)` позволяет выполнять `REFRESH MATERIALIZED VIEW CONCURRENTLY` —
без блокировки читателей.

## Иерархия lab.geo_tree

```
BR                                  (country, корень, parent_id = NULL)
├── ST:SP                           (state, 20 городов)
│   ├── CTY:SP:sao paulo            (city)
│   └── ... ещё 19 городов
├── ST:GO                           (state, 20 городов) — корень варианта 10
│   ├── CTY:GO:goiania              (city)
│   └── ... ещё 19 городов
└── ...  всего 27 штатов
```

Правила построения:

* `node_id` = `'BR'` для корня, `'ST:<код штата>'` для штата, `'CTY:<штат>:<город>'` для города;
* города отобраны через `ROW_NUMBER() OVER (PARTITION BY customer_state ORDER BY count(*) DESC, customer_city)`
  с условием `city_rank <= 20`, то есть в каждом штате не больше 20 городов по числу клиентов;
* внешний ключ `parent_id → lab.geo_tree(node_id)` следит за целостностью ссылок, а не за
  ацикличностью: цикл (например, корень, ставший потомком собственного города) база не запретит.

Получилось **495 узлов**: 1 страна + 27 штатов + **467 городов**. Двадцать городов набралось
у 22 штатов, у остальных в Olist меньше городов: AC — 8, AP — 6, DF — 6, AM — 5, RR — 2.
Штат GO (вариант 10) — **20 из 178** городов Olist.

## Рекурсивный запрос: базовая и рекурсивная часть

```sql
WITH RECURSIVE geo_subtree AS (
    SELECT g.node_id, g.parent_id, g.node_name, g.node_type, 0 AS depth, g.node_name::text AS path
    FROM lab.geo_tree AS g
    WHERE g.node_id = 'ST:GO'
    UNION ALL
    SELECT c.node_id, c.parent_id, c.node_name, c.node_type,
           p.depth + 1, p.path || ' > ' || c.node_name
    FROM lab.geo_tree AS c
    JOIN geo_subtree AS p ON c.parent_id = p.node_id
)
SELECT depth, node_id, path, node_name FROM geo_subtree ORDER BY path;
```

* **Базовая часть** (`SELECT ... WHERE node_id = 'ST:GO'`) выполняется один раз и создаёт
  начальное множество — одну строку с корнем варианта, `depth = 0`.
* **Рекурсивная часть** ссылается на `geo_subtree` как на таблицу предыдущей итерации: она
  добавляет детей уже найденных узлов (`c.parent_id = p.node_id`) и увеличивает `depth` на 1.
* Условие завершения — момент, когда рекурсивная часть не добавляет новых строк (неподвижная
  точка). Для дерева это листья, у которых нет детей; база нигде не задаёт «глубину остановки».
  Оператор `UNION ALL` сохраняет дубликаты строк, поэтому на графе **с циклом** этот запрос
  никогда не завершится, а на дереве проблемы нет.

**Результат для варианта 10 — ровно 21 строка**: `depth 0` — сам штат GO (`path = 'GO'`),
`depth 1` — его 20 городов. Пример строк:

| depth | node_id | path | node_name |
| --- | --- | --- | --- |
| 0 | ST:GO | GO | GO |
| 1 | CTY:GO:anapolis | GO > anapolis | anapolis |
| 1 | CTY:GO:goiania | GO > goiania | goiania |

`path` собран как `parent.path || ' > ' || node_name`: путь родителя вычисляется на предыдущей
итерации, поэтому он всегда готов к моменту добавления потомка, и никакого «обратного
соединения» не нужно. Для трёхуровневой иерархии можно было бы взять
`g.node_name || ' > ' || p.node_name`, но накопление пути работает для дерева любой глубины.

**Обратный обход** (п. 6) устроен зеркально: базовая часть — выбранный город `CTY:GO:goiania`,
рекурсивная часть поднимается к родителю (`JOIN ... ON c.parent_id = p.node_id`),
условие завершения — у `BR` нет родителя. Результат — 3 строки:

| depth | node_id | node_name | node_type |
| --- | --- | --- | --- |
| 0 | CTY:GO:goiania | goiania | city |
| 1 | ST:GO | GO | state |
| 2 | BR | Brazil | country |

## Сколько потомков у каждого штата (п. 7)

Две меры:

* скоррелированный рекурсивный подзапрос в списке `SELECT` — для каждого из 27 штатов считает
  размер поддерева (`count(*) - 1`, то есть без самого штата);
* CTE `geo_reach` — транзитивное замыкание ребра `parent_id`, стартующее сразу от всех штатов,
  с числом шагов `hops`; отсюда число потомков, число потомков-городов и максимальная глубина.

Обе дают одинаковые числа, например **ST:GO → 20** в обоих запросах. Топ-10 штатов:

| state_node | descendants_total | cities_in_subtree | max_depth |
| --- | --- | --- | --- |
| ST:AL … ST:TO (22 штата) | 20 | 20 | 1 |
| ST:AC | 8 | 8 | 1 |
| ST:AP | 6 | 6 | 1 |
| ST:DF | 6 | 6 | 1 |
| ST:AM | 5 | 5 | 1 |
| ST:RR | 2 | 2 | 1 |

Все потомки штата — города (глубина 1), поэтому у штата 22 города — максимум, а у «бедных»
штатов top-20-фильтр не срабатывает.

## Защита рекурсии от цикла (п. 8*)

Копия `lab.geo_tree_cyclic` повторяет рабочее дерево, а затем **корню `BR` назначается родитель
`CTY:GO:goiania`**: город ведёт к `ST:GO`, `ST:GO` — к `BR`, `BR` — обратно к городу. Получается
цикл `BR → ST:GO → CTY:GO:goiania → BR`, и обычный обход без `CYCLE` из п. 5 на такой таблице
никогда не остановится. Два способа завершения рекурсии:

1. **Клауза `CYCLE`** (SQL:2003, есть в PostgreSQL 14+):

   ```sql
   WITH RECURSIVE ... 
   CYCLE node_id SET is_cycle USING path
   ```

   База ведёт подсчёт появления каждого `node_id` в пути обхода и как только узел повторяется,
   помечает строку `is_cycle = true` и не раскрывает её дальше. Результат — **496 строк**:
   495 настоящих узлов дерева плюс одна повторная строка `BR` на `depth 3` с `is_cycle = t`.
   Других `is_cycle = t` строк нет, значит обход по рабочему дереву не пострадал — клауза
   обрывает ровно цикл и ничего больше.
2. **Глубинный предохранитель**: `WHERE p.depth < 100`. Обход гарантированно завершается, но
   размножает строки: результат — **16 363 строки** при 495 различных узлах, `max_depth = 100`,
   узел `BR` встретился 34 раза (по одному разу на каждые три шага цикла, то есть цикл
   `BR → ST:GO → CTY:GO:goiania` прошёлся ~33 раза).
   Это страховка от зависания, а не исправление данных — цикл в таблице остаётся.

Правильное решение — **не хранить цикл в рабочем дереве**: `lab.geo_tree` его не содержит, а
зацикленные иерархии ищут отдельным запросом (например, обход от всех листьев вверх с поиском
повтора). Именно поэтому циклическая копия — отдельная таблица, а не строка в рабочем дереве.

## Как запустить

```bash
psql -h localhost -p 5432 -U student -d olist -f lab10/lab10.sql
```

или в DBeaver: открыть `lab10.sql` и выполнить как один скрипт (`Alt+X`) либо по оператору
(`Ctrl+Enter`). Каждый оператор независим, поэтому можно запускать по одному в любом
порядке — все объекты пересоздаются с нуля.
