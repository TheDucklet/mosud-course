# Практика 9. Функциональные зависимости и нормализация

**Вариант 10. Исходное отношение**

```
transfer_flat(transfer_id, source_wh, source_city, dest_wh, dest_city,
              product_id, category_name, qty, created_at)
```

**Бизнес-правила, заданные в задании**

1. склад → город: у склада ровно один город;
2. товар → категория: у товара ровно одна категория;
3. перемещение → источник, назначение, дата: шапка перемещения определяет маршрут и дату;
4. (перемещение, товар) → количество: количество задаётся парой «перемещение + товар».

---

## 1. Функциональные зависимости

Из бизнес-правил получается множество ФЗ (с транзитивными замыканиями):

| № | ФЗ | Откуда следует |
|---|---|---|
| F1 | `source_wh → source_city` | склад-источник имеет один город |
| F2 | `dest_wh → dest_city` | склад-назначение имеет один город |
| F3 | `product_id → category_name` | у товара одна категория |
| F4 | `transfer_id → source_wh, dest_wh, created_at` | шапка перемещения определяет маршрут и дату |
| F5 | `(transfer_id, product_id) → qty` | количество — атрибут конкретной позиции |

Заметим, что F1 и F2 — это одна и та же зависимость «склад → город», записанная для двух
ролей склада в отношении; при декомпозиции склады объединяются в один справочник.

## 2. Замыкание атрибутов и потенциальные ключи

Отношение: R = (transfer_id, source_wh, source_city, dest_wh, dest_city, product_id,
category_name, qty, created_at).

**Замыкание** `{transfer_id, product_id}+`.  Начинаем с X = {transfer_id, product_id}:

* по F4 добавляем `source_wh, dest_wh, created_at` → X = {transfer_id, product_id, source_wh, dest_wh, created_at};
* по F1, F2 добавляем `source_city, dest_city` → X = {…, source_city, dest_city};
* по F3 добавляем `category_name`;
* по F5 добавляем `qty` → X = все девять атрибутов.

Значит, `{transfer_id, product_id}+ = U`, то есть **`(transfer_id, product_id)` — суперключ**.

**Минимальность.** Уберём `transfer_id`: `{product_id}+ = {product_id, category_name}` ≠ U.
Уберём `product_id`: `{transfer_id}+ = {transfer_id, source_wh, source_city, dest_wh, dest_city,
created_at}` ≠ U (не содержит `qty`). Ни один атрибут убрать нельзя, поэтому
**`{transfer_id, product_id}` — минимальный ключ, и он единственный**: любой другой набор без
одного из этих двух атрибутов не выводит `qty`, а `qty` не выводится ни из чего другого (F5 — единственная
зависимость с `qty` в правой части).

Итог: **единственный потенциальный ключ — `(transfer_id, product_id)`**, все остальные атрибуты —
неключевые. Это сразу показывает, что отношение не находится ни в 3НФ, ни в НФБК.

## 3. Частичные и транзитивные зависимости

**Частичные зависимости** (от части составного ключа):

* `transfer_id → source_wh, dest_wh, created_at` (F4) — правая часть зависит только от
  `transfer_id`, а не от всей пары `(transfer_id, product_id)`;
* `transfer_id → source_city, dest_city` — транзитивно через F1/F2 от той же части ключа;
* `product_id → category_name` (F3) — зависит только от `product_id`.

Именно эти зависимости нарушают 2НФ.

**Транзитивные зависимости** (уже после устранения частичных):

* `source_wh → source_city`, где `source_wh` — неключевой атрибут … но строго говоря, для нарушения
  3НФ нужна зависимость неключевого атрибута от ключа через другой неключевой атрибут:
  `(transfer_id, product_id) → source_wh → source_city` (аналогично `dest_wh → dest_city` и
  `product_id → category_name`). Это транзитивные зависимости через неключевой атрибут.
* В изменённой проекции на шапку `(transfer_id, source_wh, dest_wh, created_at)` частичных
  зависимостей нет (ключ — `transfer_id`), но `source_wh → source_city` остаётся транзитивной,
  если хранить город в шапке.

## 4. Аномалии исходного плоского отношения

Исходные данные (5 строк, 4 перемещения — у перемещения 2 две позиции):

| transfer_id | source_wh | source_city | dest_wh | dest_city | product_id (начало) | category_name | qty | created_at |
|---|---|---|---|---|---|---|---|---|
| 1 | WH-SP01 | sao paulo | WH-RJ01 | rio de janeiro | `154e7e31…` | beleza_saude | 3 | 2018-01-10 09:00 |
| 2 | WH-RJ01 | rio de janeiro | WH-POA1 | porto alegre | `154e7e31…` | beleza_saude | 2 | 2018-01-12 14:30 |
| 2 | WH-RJ01 | rio de janeiro | WH-POA1 | porto alegre | `2b4609f8…` | beleza_saude | 1 | 2018-01-12 14:30 |
| 3 | WH-SP01 | sao paulo | WH-CWB1 | curitiba | `154e7e31…` | beleza_saude | 5 | 2018-02-01 11:15 |
| 4 | WH-POA1 | porto alegre | WH-SP01 | sao paulo | `7c1bd920…` | beleza_saude | 4 | 2018-02-20 08:45 |

> Товары — реальные `product_id` из `olist.products` (префиксы приведены для читаемости; полное
> значение — 32 шестнадцатеричных символа). Скрипт подставляет их через `INSERT … SELECT` с
> `LIMIT 1 … OFFSET <слот>`, поэтому идентификаторы всегда существуют в Olist и повторяемы.

Уже в этих пяти строках видно избыточность: `rio de janeiro` записан 3 раза (строки 1–3),
`sao paulo` — 3 раза (строки 1, 3, 4), `beleza_saude` — 5 раз, хотя различных товаров всего 3,
а складов — 4.

**Аномалия INSERT — нельзя ввести факт о складе или товаре без перемещения.**
Чтобы зарегистрировать новый склад `WH-BSB1` в Бразилиа, нужно придумать фиктивное перемещение
с фиктивным товаром, иначе в таблице не будет строки, где хранится город этого склада. То же
верно для категории нового товара: категория существует только вместе с перемещением.

**Аномалия UPDATE — изменение справочного значения в нескольких строках.**
Если склад `WH-RJ01` переехал и его город меняется с `rio de janeiro` на `niteroi`, нужно
обновить все 3 строки, где этот склад встречается (и как источник в строке 2, и как назначение
в строке 1). Аналогично для `WH-SP01` — 3 строки. Если обновить только одну строку, один и тот же
код склада `WH-RJ01` получит два разных города, и ФЗ `warehouse → city` окажется нарушенной прямо
в данных. В плоской таблице это ничем не запрещено: ни `PK`, ни `CHECK`, ни `FK` не мешают
разным строкам приписать одному складу разные города.

**Аномалия DELETE — потеря последнего факта о справочном значении.**
Удаление последнего перемещения, в котором участвовал склад (`WH-CWB1` встречается только в
перемещении 3), стирает и единственную запись о городе `curitiba` — справочная информация исчезает
вместе со «случайной» транзакционной строкой. Та же проблема с категорией товара `7c1bd920…`:
если удалить перемещение 4.

## 5. Декомпозиция до 3НФ по шагам

### Шаг 1. Вынести `warehouse → city` из плоского отношения

Причина разбиения: **F1/F2** (`source_wh → source_city`, `dest_wh → dest_city`), нарушающие 3НФ
через часть ключа и через неключевой атрибут.

```
R1(wh_code, city)                     -- PK wh_code
R2(transfer_id, source_wh, dest_wh, created_at, product_id, category_name, qty)
```

Частичная зависимость `transfer_id → source_city` и транзитивная `source_wh → source_city`
устранены; город теперь хранится один раз на склад.

### Шаг 2. Вынести `product_id → category_name`

Причина разбиения: **F3** (`product_id → category_name`) — частичная зависимость от части
составного ключа `(transfer_id, product_id)` и транзитивная зависимость ключа через неключевой
`product_id`.

```
R1(wh_code, city)                          -- PK wh_code
R3(product_id, category_name)              -- PK product_id
R4(transfer_id, product_id, qty, source_wh, dest_wh, created_at)
```

### Шаг 3. Вынести шапку перемещения `transfer_id → source_wh, dest_wh, created_at`

Причина разбиения: **F4** — частичная зависимость от части ключа `transfer_id`, из-за неё
маршрут и дата повторялись для каждой позиции одного перемещения (в исходных данных
перемещение 2 занимает 2 строки).

```
R1(wh_code, city)                                    -- PK wh_code
R3(product_id, category_name)                        -- PK product_id
R5(transfer_id, source_wh, dest_wh, created_at)      -- PK transfer_id
R6(transfer_id, product_id, qty)                     -- PK (transfer_id, product_id)
```

Теперь остаются только ключевые зависимости:

* в R1 `wh_code → city` — детерминант — суперключ;
* в R3 `product_id → category_name` — суперключ;
* в R5 `transfer_id → source_wh, dest_wh, created_at` — суперключ;
* в R6 `(transfer_id, product_id) → qty` — суперключ.

Частичных и транзитивных зависимостей нет: **схема в 3НФ**.

## 6. Проверка НФБК

НФБК: детерминант каждой нетривиальной ФЗ — суперключ. Проверяем детерминанты:

| Отношение | Детерминанты | Суперключ? | НФБК |
|---|---|---|---|
| `nf_transfer_warehouse(wh_code, city)` | `wh_code` | да (PK) | да |
| `nf_transfer_product(product_id, category_name)` | `product_id` | да (PK) | да |
| `nf_transfer(transfer_id, source_wh, dest_wh, created_at)` | `transfer_id`; `(source_wh, dest_wh, created_at)` (по `UNIQUE`) | да | да |
| `nf_transfer_item(transfer_id, product_id, qty)` | `(transfer_id, product_id)` | да (PK) | да |

Все отношения находятся сразу и в 3НФ, и в **НФБК** — в 3НФ-разложении нет неключевых
детерминантов, так что дополнительного разбиения для НФБК не требуется, и **все исходные ФЗ
F1–F5 сохранены** (F1/F2 — в R1, F3 — в R3, F4 — в R5, F5 — в R6). Поэтому потери важных
зависимостей нет.

## 7. Соединение без потерь и сохранение зависимостей

**Без потерь (lossless join).** Декомпозиция на каждом шаге выполняется по ФЗ `X → Y`, для которой
`X ∩ Y` — ключ в выделенном отношении (`wh_code`, `product_id`, `transfer_id`). По теореме Хита такая
декомпозиция сохраняет соединение. Практическая проверка — в скрипте (запрос «проверка равенства»):
соединение четырёх нормализованных отношений даёт 5 строк, операция `EXCEPT` находит 0
отличающихся строк, т.е. восстанавливается ровно исходное `nf_transfer_flat`.

**Сохранение зависимостей.** Каждая ФЗ после разложения присутствует внутри одного отношения:
F1 и F2 — в `nf_transfer_warehouse` (роли источника и назначения ссылаются на один справочник),
F3 — в `nf_transfer_product`, F4 — в `nf_transfer`, F5 — в `nf_transfer_item`. Ни одной ФЗ,
требующей соединения для проверки, не осталось (это и есть свойство «dependency preserving»).

## 8. Реализация в PostgreSQL

Все объекты — в схеме `lab`, исходный `olist` не изменяется. Скрипт идемпотентен:
пять `DROP TABLE IF EXISTS … CASCADE` перед созданием.

| Отношение | Ключи и ограничения |
|---|---|
| `lab.nf_transfer_flat` | `pk_nf_transfer_flat (transfer_id, product_id)`, `ck_…_qty (qty > 0)`, `ck_…_warehouses (source_wh <> dest_wh)` — исходное отношение для демонстрации избыточности |
| `lab.nf_transfer_warehouse` | `pk_nf_transfer_warehouse (wh_code)`, `ck_…_code (wh_code ~ '^WH-[A-Z0-9]+$')` |
| `lab.nf_transfer_product` | `pk_nf_transfer_product (product_id)`, `fk_nf_transfer_product_olist → olist.products(product_id)` |
| `lab.nf_transfer` | `pk_nf_transfer (transfer_id)`, `uq_nf_transfer_route (source_wh, dest_wh, created_at)`, `fk_…_source`/`fk_…_dest → lab.nf_transfer_warehouse`, `ck_…_warehouses (source_wh <> dest_wh)` |
| `lab.nf_transfer_item` | `pk_nf_transfer_item (transfer_id, product_id)`, `fk_…_transfer → lab.nf_transfer`, `fk_…_product → lab.nf_transfer_product`, `ck_…_qty (qty > 0)` |

Справочные `nf_transfer_warehouse` и `nf_transfer_product` соединяются с реальным Olist: товары —
через `FK` на `olist.products`, города и коды складов — из данных Olist-городов (те же значения, что
используются в Практике 8).

## 9. Ответы на контрольные вопросы

1. **Что означает замыкание множества атрибутов?** Замыкание `X+` — это множество всех атрибутов
   отношения, которые можно вывести из `X`, многократно применяя заданные ФЗ (правила
   рефлексивности, пополнения, транзитивности). В работе `{transfer_id, product_id}+ = U`, поэтому
   эта пара — ключ, а `{product_id}+ = {product_id, category_name}` ≠ U — значит, ключ минимален.
2. **Чем 3НФ отличается от НФБК?** В 3НФ неключевой атрибут не должен зависеть транзитивно от
   ключа; детерминантом нетривиальной ФЗ может быть «почти ключ», если он состоит только из
   ключевых атрибутов. В НФБК требуется, чтобы детерминант каждой нетривиальной ФЗ был
   суперключом вообще. Они совпадают, когда ключ простой, и различаются для отношения с
   несколькими перекрывающимися составными ключами. В этой работе после декомпозиции все
   детерминанты — ключи, поэтому схема в НФБК.
3. **Что значит «декомпозиция без потерь»?** Это значит, что обратное соединение выделенных
   отношений даёт ровно исходное отношение — ни одна строка не теряется и не дублируется.
   Проверено теоремой Хита для каждого шага (общий детерминант — ключ разбиваемого отношения)
   и практическим запросом с `EXCEPT`: 0 строк различаются.
