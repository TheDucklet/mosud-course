**Вариант:** 10 — множество штатов S = {AL, SE, BA}.
**СУБД:** PostgreSQL 17, база `olist` (схема `olist` только читается).

## Что делает работа

Для множества штатов S = {AL, SE, BA} найти товарные категории, которые встречались
в **доставленных** заказах покупателей **каждого** штата из S, — это классическое
реляционное деление `C ÷ S`. Задача решена несколькими независимыми способами
(двойной `NOT EXISTS`, `GROUP BY … HAVING count(DISTINCT …)`, `EXCEPT`), их
эквивалентность доказана запросами `EXCEPT` в обе стороны, отдельно разобрано
поведение при пустом делителе, и дополнительно (пункт 8) то же деление применено
к продавцам.

Формально: делимое — множество категорий `C`, делитель — множество штатов `S`,
отношение `D(c, s)` — «категория `c` встречалась хотя бы в одном доставленном заказе
покупателя из штата `s`». Результат:

    C ÷ S = { c ∈ C | ∀ s ∈ S : D(c, s) }.

## Как устроены блоки

1. **Входные данные.** CTE `target_states` — это делитель: три литерала в `VALUES`.
   Мощность делителя нигде не зашита константой, она считается как
   `(SELECT count(*) FROM target_states)`. CTE `delivered_items` строит отношение `D`:
   `orders ⨝ customers ⨝ order_items ⨝ products` с фильтрами `order_status = 'delivered'`,
   `customer_state IN (SELECT state FROM target_states)` и
   `product_category_name IS NOT NULL`. Сводный запрос показывает размеры числителя
   и делителя, чтобы дальше было с чем сравнивать результат.
2. **Пункт 2 — двойной `NOT EXISTS`.** Читается как двойное отрицание:
   *«нет такого штата s из S, для которого не найдётся категории c в штате s»*.
   Внутренний `NOT EXISTS` — это `¬∃d`, внешний — ещё одно `¬∃s`; вместе
   `¬∃s ¬∃d ≡ ∀s ∃d`, то есть буквальная запись `∀` из постановки задачи.
   Корреляция нужна на двух уровнях: `di.category = ci.category` (внешний запрос
   `categories_in_s`) и `di.customer_state = ts.state` (средний уровень
   `target_states`). Второй запрос пункта добавляет к каждой категории число покрытых
   штатов (у всех найденных оно равно 3 — это и есть визуальная проверка `∀`),
   число заказов и английское название категории.
3. **Пункт 3 — `GROUP BY … HAVING count(DISTINCT customer_state) = |S|`.**
   Для каждой категории смотрим, в скольких **разных** штатах она встречалась;
   «встречалась во всех» ⇔ «число разных штатов равно мощности делителя».
   Сравнение с `(SELECT count(*) FROM target_states)` привязывает запрос к делителю:
   поменяв набор штатов в `VALUES`, больше ничего править не нужно. `DISTINCT`
   обязателен — без него счётчик считал бы заказы (в BA их тысячи), а не штаты.
4. **Пункт 4 — через `EXCEPT`.** Идея: «категория покрывает все штаты» ⇔ «среди всех
   пар (категория, штат) нет ни одной непокрытой». `missing_pairs` = `categories_in_s
   CROSS JOIN target_states` (все пары `C × S`) `EXCEPT` реально встреченные пары
   `(category, customer_state)`; `EXCEPT` — операция над множествами, дубликаты она
   удаляет сама. Затем `categories_in_s EXCEPT` категории, у которых есть хотя бы одна
   пропущенная пара (вторая часть пункта — `NOT EXISTS` по `missing_pairs`), даёт 35
   категорий. Важная деталь: `EXCEPT` требует одинаковый набор и порядок столбцов,
   поэтому промежуточные наборы проецируются на один столбец `category`.
5. **Пункт 5 — доказательство эквивалентности.** Сначала вычисляются мощности всех
   трёх наборов (35 / 35 / 35), затем — шесть проверок `A EXCEPT B` и `B EXCEPT A`
   для всех пар наборов. Все шесть дают 0, значит наборы совпадают как множества строк.
   Порядок важен: сначала полностью вычисляются наборы, и только потом к результату
   применяется метка `label`; если включить метку в сами `EXCEPT`, разность всегда
   будет пустой, и проверка ничего не докажет.
6. **Пункт 6 — диагностика.** Для категории-лидера по числу заказов выводится
   таблица «категория → штат → число заказов» с числом продавцов и долей штата.
   Второй запрос по той же категории оформлен через `GROUPING SETS ((state), ())`
   и `FILTER`: он даёт строки по штатам и строку «ИТОГО» за один проход.
   Диагностика показывает, что популярность категории в S держится на BA
   (319 из 419 заказов) — это и есть цена «лидерства» в делимом.
7. **Пункт 7 — пустой делитель.** `target_states` пуст (`WHERE false`), а делимое —
   **каталог** `DISTINCT product_category_name` из `products` (73 категории, не пустой).
   Результат: `NOT EXISTS` → **73** (все категории), `HAVING` → **0**, `EXCEPT` → **73**.
   Причина: `∀s∈∅ P(s)` истинно **вакуумно**, поэтому двойной `NOT EXISTS` возвращает
   всё делимое; `count(DISTINCT …) = 0` не выполняется ни для одной непустой группы
   (`delivered_items` пуст, групп нет вовсе); в `EXCEPT`-решении пары
   «категория × штат» тоже пусты, поэтому вычитать из каталога нечего — остаётся
   весь каталог. Так и проявляется двойственность пустого делителя: `NOT EXISTS`
   следует математике («ограничений нет — подходит всё»), а `HAVING` — синтаксису
   группировки («групп нет — строк нет»). Пустой делитель нужно доопределять
   в постановке задачи — см. вопрос 3.
8. **Пункт 8 — продавцы.** Тот же приём деления применён к `order_items.seller_id`:
   делимое — продавцы (1051 кандидат, у которых есть хотя бы одна доставленная позиция
   в S), делитель — те же три штата, `D(seller, state)` — продажа заказа в этот штат.
   Три реализации дают **70** продавцов, обе проверки `EXCEPT` — 0. Второй запрос
   показывает разбивку заказов каждого такого продавца по AL/SE/BA и его город.
   Самым «всесторонним» оказался продавец `6560211a19b47992c3666cc44a7e94c0` из
   Сан-Паулу: 97 заказов в S (AL 6, SE 9, BA 82).

## Что показывают пункты 2–5 и почему этому можно верить

- Три реализации — разные записи одного предиката `∀`; все дают одно и то же
  множество из 35 категорий, а `EXCEPT` в обе стороны подтверждает совпадение.
- Кандидатов 63, прошли 35. Категория может быть популярной и всё равно не пройти:
  `utilidades_domesticas` есть в BA и SE, но не в AL. Это не ошибка, а свойство данных:
  AL и SE — малые штаты (позиций с известной категорией в AL — 423, в SE — 373,
  в BA — 3625), поэтому в AL «пропущена» 21 категория, в SE — 22, а в BA — лишь одна.
- `NOT EXISTS` — «родная» форма реляционного деления: синтаксис прямо повторяет
  квантор, не нужны ни `DISTINCT`, ни знание мощности делителя, и поведение при
  пустом делителе соответствует математике. `HAVING` короче, но требует, чтобы делимое
  уже было соединено с делителем (при пустом S соединение даёт пустой набор).
  `EXCEPT` хорошо читается математически, но требует согласованных наборов столбцов.

## Контрольные вопросы

1. **Как переписать «для всех x выполняется P(x)» через «не существует»?**
   `∀x P(x) ≡ ¬∃x ¬P(x)`. В SQL это `NOT EXISTS (SELECT 1 FROM X WHERE NOT EXISTS
   (SELECT 1 FROM D WHERE … ))`: внешний `NOT EXISTS` — `¬∃` по элементам делимого,
   внутренний — отрицание предиката `¬P(x)`. В нашей задаче `¬∃s ¬∃d ≡ ∀s ∃d`:
   «не существует штата, в котором категории нет» = «категория есть в каждом штате».
2. **Почему `count(DISTINCT customer_state)` сравнивают с мощностью делителя?**
   Для категории `count(DISTINCT customer_state)` — это число штатов из S, в которых она
   встретилась. «Встретилась во всех» ⇔ «их столько же, сколько в S»: для любого
   `X ⊆ S` выполняется `X = S ⇔ |X| = |S|`. Сравнение с константой 3 формально верно
   только для этого варианта и опасно при его смене; сравнение с
   `(SELECT count(*) FROM target_states)` привязано к делителю. И `DISTINCT`
   обязателен: без него счётчик считал бы заказы, и сравнивать его с `|S|` бессмысленно.
3. **Что будет с универсальным условием, если множество обязательных элементов пусто?**
   Оно истинно **вакуумно**: контрпримера («такого s, где P(s) ложно») не существует,
   значит «∀s P(s)» истинно. Поэтому `NOT EXISTS`-решение при пустом S возвращает всё
   делимое (73 категории каталога): ограничений нет — подходит всё. Решение через
   `HAVING` перебирает группы и при пустом S не даёт групп вообще; решение через
   `EXCEPT` при пустом S вычитает пустое множество и тоже возвращает весь каталог.
   Практический вывод: пустой делитель нужно явно доопределить в постановке задачи,
   а не надеяться, что все реализации совпадут.
